# CONSTITUTION
# Ablation Constitution

**Version:** 1.0

This constitution controls automated three-model framework ablations. It must be frozen before an ablation begins and may not be changed in response to that ablation's results.

## 1. Separation of duties

For each ablation:

- exactly one model is Builder;
- exactly one different model is Validator;
- exactly one third model is Adjudicator;
- no model may hold more than one role;
- Builder and Validator first-pass outputs are blind to one another;
- the Adjudicator receives only frozen evidence after Builder and Validator packs are complete.

## 2. Frozen inputs

The following must be frozen before execution:

- baseline framework version;
- ablation specification;
- fixture suite;
- critical reconciliation field list;
- allowed source/data scope;
- expected unchanged surfaces;
- operational benefit predicate;
- regression rule;
- model-role assignment;
- constitution version.

Missing frozen inputs require **HALT**.

## 3. Evidence requirement

A claim that a test passed is not evidence by itself.

Required mechanical claims must be backed by raw execution evidence where applicable:

- stdout/stderr;
- SQL/R/tool output;
- fixture actuals and expecteds;
- reconciliation output;
- diff output;
- file manifests;
- SHA-256 hashes.

If a required raw artifact is unavailable, return **HALT**.

## 4. Hard mechanical agreement

Builder and Validator must agree on all predeclared hard mechanical facts.

Examples include:

- `mismatch_count == 0` on the frozen critical-field list;
- fixture IDs executed;
- expected versus actual fixture results;
- baseline and candidate version hashes;
- declared changed-file set;
- source row counts where specified;
- required output existence.

If Builder and Validator disagree on a hard mechanical fact, return **HALT**.

Do not silently REVERT. Mechanical disagreement means the harness or implementation requires diagnosis.

## 5. Semantic protection

Schema equality alone does not prove semantic equality.

The ablation must therefore use both:

- deterministic file/schema/configuration diffing; and
- locked behavioral fixtures covering the decision-changing semantics relevant to the change.

Any undeclared semantic change returns **REVERT** unless the disagreement itself makes the harness suspect, in which case return **HALT**.

## 6. Benefit predicate

Every ablation must state an operational benefit predicate before execution.

The predicate must be checkable from frozen artifacts without asking the Builder what it meant.

Valid forms include:

- detection of a seeded failure missed by baseline;
- removal of redundant complexity with unchanged detection coverage and outputs;
- elimination of a documented ambiguity demonstrated by independent implementation;
- detection of a seeded Stage 4 delivery/implementation defect;
- measurable reduction in unnecessary steps while all required safeguards remain green.

A subjective statement such as "the change is better" is invalid and requires **HALT** before execution.

## 7. KEEP rule

Return **KEEP** only when all are true:

1. evidence packs are complete and frozen;
2. role separation is valid;
3. Builder and Validator agree on hard mechanical facts;
4. exact reconciliation passes where required;
5. every mandatory fixture passes;
6. no undeclared semantic change is detected;
7. no locked regression is introduced;
8. the predeclared benefit predicate is satisfied;
9. no blocking objection remains supported by the frozen evidence.

All nine conditions are conjunctive.

## 8. REVERT rule

Return **REVERT** when:

- the mechanics are internally coherent;
- HALT conditions are absent;
- but one or more KEEP conditions are not established.

REVERT is the conservative default for unresolved soft judgment.

## 9. HALT rule

Return **HALT** when:

- hard mechanical results conflict;
- required raw evidence is missing;
- hashes or frozen versions mismatch;
- the baseline or constitution changed mid-run;
- role separation was violated;
- information barriers were breached before first-pass freeze;
- the benefit predicate was not operationally defined before execution;
- the adjudicator cannot determine which frozen evidence pack is authoritative.

HALT means the experiment is not valid enough to adjudicate.

## 10. Adjudicator limits

The Adjudicator may not:

- create a new success criterion;
- relax a failed hard gate;
- choose one mechanical result over another when Builder and Validator conflict;
- modify Builder or Validator artifacts;
- repair code;
- rerun the ablation and substitute its own result;
- use majority vote to override the constitution.

It must cite the frozen evidence supporting each constitutional condition.

## 11. Constitution changes

This constitution may not self-modify during an ablation.

A proposed change to the constitution must be treated as a separate meta-ablation with:

- a frozen prior constitution;
- a declared proposed revision;
- independent Builder/Validator analysis;
- third-model adjudication;
- deterministic evidence freezing.

## 12. Final rule

> **Hard disagreement halts. Coherent evidence without proven benefit reverts. Only independently reproduced, regression-free, predeclared benefit is kept.**---

YYYY-MM-DD HH:MM:SS
A date must be a valid Gregorian calendar date with valid clock components.
Additional source formats, fractional seconds, or timezone offsets require explicit profiling and a locked parsing extension.
For the primary calendar-day calculation:
- Treat source date text as a civil calendar date.
- Do not convert it to UTC or calculate elapsed seconds.
- Do not assume an official City timezone convention.
- If timezone-bearing formats are present and their date interpretation changes the result, retain an uncertainty branch until semantics are approved.
The America/Chicago reference describes the portfolio simulation's intended local calendar. It is not proof that the source timestamps were recorded in that timezone.
6.5 Date-boundary rules
- Same reference date: age zero.
- Creation before the reference date: nonnegative integer calendar age.
- Creation after the reference date: INCONCLUSIVE.
- Missing/unparseable creation date: INCONCLUSIVE.
- Exact threshold equality: ESCALATE if all integrity conditions pass.
- No rounding of dates to hours or seconds for the primary rule.
A date-level calculation deliberately avoids unsupported hour-level precision and DST ambiguity.

8. Primary KPI and Evidence Contracts
8.1 Primary request-level evidence
Metric: open_age_calendar_days
Purpose: Measure unresolved calendar age under the portfolio reference date.
Grain: One eligible request.
Definition:
\[
A_i =
\operatorname{ordinal}(D_{\text{reference}})
-
\operatorname{ordinal}(D_{\text{created},i})
\]

where ordinal is a calendar-day index.
Units: Whole calendar days.
Precision: Exact integer.
Direction: Higher values indicate greater elapsed unresolved age under the heuristic; they do not establish greater harm.
Missingness: Undefined age triggers INCONCLUSIVE for otherwise eligible rows.
Weighting: One request, one observation.
Decision threshold: \(A_i \ge K\).
8.2 Primary portfolio KPI
Name: Escalation Candidate Share
\[
\text{ECS} =
\frac{N_{\text{ESCALATE}}}
{N_{\text{eligible}}}
\]

Numerator: Number of eligible requests assigned ESCALATE.
Denominator: All eligible snapshot-open requests, including INCONCLUSIVE.
Unit: Proportion, displayed as a percentage.
Aggregation: Each request has unit weight.
Internal precision: Unrounded integer components and full-precision ratio.
Display: Counts as integers; shares to two decimal places.
Direction: Descriptive, not an optimization target. Neither a larger nor a smaller share is intrinsically better.
The denominator includes INCONCLUSIVE because otherwise the measure could look artificially favorable when evidence quality deteriorates.
8.3 Companion classification KPI
Name: Conclusive Classification Share
\[
\text{CCS} =
\frac{N_{\text{ESCALATE}}+N_{\text{STANDARD}}}
{N_{\text{eligible}}}
\]

This records how much of the approved decision universe received a conclusive age-based assignment.
It is a quality guardrail, not a replacement for ECS.
8.4 Guardrail metrics
Metric	Contract
INCONCLUSIVE share	inconclusive_n / eligible_n
Open exclusion share	excluded_open_n / source_open_n
Creation-date failure share	Eligible records with missing/invalid CREATED_DATE divided by eligible requests
Parent ambiguity share	Eligible requests with unresolved or contradictory duplicate/parent evidence divided by eligible requests
Status/closed-date contradiction count	Source-open requests with populated CLOSED_DATE
Type coverage	Eligible rows with a usable SR_TYPE divided by eligible requests
Escalation concentration	Share of ESCALATE requests in each reported type or geographic segment
Zero denominators yield undefined rates, never silently zero.
Raw components must always accompany percentages.
8.5 Diagnostic metrics
- Request age distribution: median, P75, P90.
- Age distribution separately for ESCALATE, INCONCLUSIVE, and STANDARD where defined.
- SR_TYPE and SR_SHORT_CODE composition.
- WARD and COMMUNITY_AREA composition.
- LAST_MODIFIED_DATE recency where parseable.
- Duplicate/parent and legacy flag distributions.
- Counts of source-open requests with closed-date evidence.
- Exact status versus closed-date cross-tabulation.
No diagnostic may alter the primary action table without returning to Design.

9. Comparison and Baseline Contract
9.1 Primary baseline
The controlling comparison is the approved threshold \(K\).
Every sufficiently evidenced eligible request is compared against the same calendar-age rule.
This is a portfolio decision cutoff, not an empirical service promise.
9.2 Why a global cutoff is proposed
A global age rule has three advantages for this first simulation:
1. It requires fewer unverified source-field semantics than a dormancy measure.
2. It can be independently reconstructed without a historical peer model.
3. It makes the owner's decision policy and its limitations explicit.
Its main weakness is also explicit: requests of different service types can have very different normal lifecycles.
Design A accepts that weakness provisionally rather than introducing a more elaborate empirical benchmark whose interpretation is not yet established.
9.3 Secondary diagnostic comparisons
Permitted comparisons include:
- ESCALATE versus STANDARD type mix.
- Within-type age distributions.
- Geographic concentration.
- Age-triggered classification versus a noncontrolling modification-dormancy diagnostic, if source semantics are profiled.
- Sensitivity of actions to fixed alternative threshold scenarios.
All comparisons use request-level weighting.
No peer benchmark is allowed to silently replace the primary decision rule.

13. Sample Size, Uncertainty, and Sensitivity
13.1 Primary classification sample size
There is no minimum sample-size requirement for assigning a deterministic age rule to an individual eligible request.
One eligible request still receives one action.
13.2 Descriptive subgroup sample size
The proposed reporting minimum of 30 applies only to displayed segment summaries.
It does not determine request eligibility or ESCALATE membership.
The reported snapshot is treated as a frozen observed population, not a random sample from which to infer exact future population parameters.
Routine sampling confidence intervals are therefore not required for the main classification shares.
13.3 Prespecified sensitivity scenarios
Primary threshold:
K = 14 calendar days
Diagnostic alternatives:
K = 7 and K = 30 calendar days.
These are frozen sensitivity scenarios, not additional owner-tunable knobs.
Expected invariant:
\[
N_E(7) \ge N_E(14) \ge N_E(30)
\]

provided that the same eligible population and integrity rules are retained.
The INCONCLUSIVE and excluded populations must remain unchanged across threshold-only sensitivity runs.
13.4 Required reporting
- Action counts under all three scenarios.
- Number and percentage of eligible requests whose actions change.
- Counts immediately around the primary threshold.
- Whether threshold changes alter the practical interpretation of the result.
- Type concentrations of threshold-sensitive cases.
Sensitivity does not authorize choosing whichever threshold produces a preferred escalation volume.

14. Decision Rule Contract
14.1 Exactly one owner-tunable knob
Property	Proposed contract
Name	open_age_days_threshold
Symbol	\(K\)
Default	14
Unit	Calendar days
Type	Integer
Allowed proposed domain	1–3,650
Threshold comparison	Greater than or equal
Status	PROVISIONAL
Authority	Human owner approval required
Interpretation	Portfolio escalation-attention cutoff
Official City SLA?	No
The value 14 is inherited as a defensible provisional candidate from the supplied coordinator proposal, not as a verified City or empirical requirement.
The allowed domain is a proposed validation constraint, not a second decision policy.
14.2 Order of evaluation
Step 0 — Source membership
A record not belonging to the frozen open source envelope receives no decision label.
Step 1 — Structural exclusions
Apply the approved exclusion hierarchy, in order:
1. Invalid identifier.
2. Confirmed information-only request.
3. Confirmed legacy request.
4. Confirmed clean duplicate child.
Excluded requests do not enter the final three-way denominator.
Step 2 — INCONCLUSIVE
For each remaining eligible request, assign INCONCLUSIVE if any material action-evidence failure exists:
- Missing or invalid creation date.
- Creation date after the approved reference date.
- Missing/blank request type.
- Populated closed date despite Open source status.
- Unknown duplicate or legacy flag.
- Contradictory duplicate/parent evidence.
- Missing or unresolved parent where the proposed duplicate-child exclusion requires one.
- Another explicitly locked critical evidence contradiction.
Step 3 — ESCALATE
If no INCONCLUSIVE condition applies:
\[
A_i \ge K \Rightarrow \text{ESCALATE}
\]

Step 4 — STANDARD
Otherwise:
\[
A_i < K \Rightarrow \text{STANDARD}
\]

14.3 Truth table
Eligible	Critical evidence sufficient	Age ≥ K	Action
No	Any	Any	Outside decision set
Yes	No	Any/unknown	INCONCLUSIVE
Yes	Yes	Yes	ESCALATE
Yes	Yes	No	STANDARD
No eligible request can receive two actions.
14.4 Reason-code precedence
For a request with multiple evidence failures, preserve every applicable failure flag, but assign one deterministic primary reason.
Proposed primary ordering:
1. BAD_CREATED_DATE
2. FUTURE_CREATED_DATE
3. OPEN_CLOSED_CONTRADICTION
4. MISSING_TYPE
5. DUPLICATE_PARENT_CONTRADICTION
6. PARENT_UNRESOLVED
7. UNKNOWN_DUPLICATE_FLAG
8. UNKNOWN_LEGACY_FLAG
9. LEGACY_REFERENCE_CONTRADICTION
For conclusive cases:
- AGE_THRESHOLD_MET
- AGE_BELOW_THRESHOLD
The reason ordering is a reporting convention; it must not change the action.
14.5 Selection field
attention_candidate = TRUE if and only if action = ESCALATE.
If a legacy field named selected is required, it has the same meaning.
It does not mean a request has been assigned actual shift capacity.
14.6 Capacity and ranking
No capacity cap, ordered rank, or tie-breaking within ESCALATE is defined.
All requests exactly at the threshold receive ESCALATE.
If the volume exceeds practical attention capacity, the resulting issue must be recorded and returned to Framing for a separate ranking or capacity decision.
Changing \(K\) merely to meet an unstated capacity target is not an authorized workaround.
14.7 Predictive analytics declaration
ml_mode = None
No training, scoring, prediction, Expand model, or post-validation predictive analysis is part of this design.
Any future model-generated score affecting action or ranking would require appropriate new design authorization.
